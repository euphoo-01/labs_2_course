# Ответы на вопросы по созданию пользовательских элементов управления

Поскольку проект разработан на современном кроссплатформенном фреймворке **Avalonia UI**, многие концепции базируются на архитектуре WPF, но имеют свои особенности реализации и названия. Для наиболее полного ответа каждый пункт разделен на две части: как это работает в классическом **WPF** и как это реализовано в нашем проекте на **Avalonia UI**.

---

### 1. Что такое Свойства зависимости (Dependency Properties)? Для чего они нужны?

**В WPF:**
Свойства зависимости (Dependency Properties, DP) — это специальный тип свойств, значение которых вычисляется динамически подсистемой WPF на основе множества источников. 
Они нужны для:
- Экономии памяти (значения по умолчанию хранятся статически и не дублируются для каждого объекта).
- Поддержки двусторонней привязки данных (Data Binding).
- Встроенной поддержки анимаций и изменения значений через стили и триггеры.
- Автоматического уведомления об изменении значений.

**В Avalonia UI:**
Концепция абсолютно идентична, но эти свойства называются **AvaloniaProperty** (а в типизированном виде — `StyledProperty`). Они решают ровно те же задачи: обеспечивают мощную систему стилей (похожую на CSS), привязку данных и анимации без лишнего расхода памяти.

---

### 2. Как создать DependencyProperty?

**В WPF:**
Создание проходит в два шага:
1. Регистрация статического поля `DependencyProperty` с помощью метода `DependencyProperty.Register`.
2. Создание стандартного CLR-свойства (свойства-обертки), где в геттере вызывается `GetValue()`, а в сеттере — `SetValue()`.
```csharp
public static readonly DependencyProperty MyProperty = 
    DependencyProperty.Register("My", typeof(int), typeof(MyControl), new PropertyMetadata(0));

public int My
{
    get { return (int)GetValue(MyProperty); }
    set { SetValue(MyProperty, value); }
}
```

**В Avalonia UI:**
Шаги аналогичны, но используется метод `AvaloniaProperty.Register<TOwner, TValue>`:
```csharp
public static readonly StyledProperty<int> MaxStarsProperty =
    AvaloniaProperty.Register<StarRatingControl, int>(nameof(MaxStars), defaultValue: 5);

public int MaxStars
{
    get => GetValue(MaxStarsProperty);
    set => SetValue(MaxStarsProperty, value);
}
```
*(Именно так реализованы свойства в наших элементах управления `StarRatingControl` и `RangeSlider`).*

### 3. Для чего и как используют делегат ValidateValueCallback?

**В WPF:**
Используется для **строгой проверки** валидности значения ДО того, как оно будет присвоено свойству. Возвращает `true` (допустимо) или `false` (выбрасывается `ArgumentException`). Метод статический и проверяет только само передаваемое значение, без доступа к экземпляру элемента управления. Передается как аргумент в `DependencyProperty.Register`.

**В Avalonia UI:**
Механизм точно такой же. Делегат передается в параметр `validate` при регистрации свойства. В нашем проекте метод `ValidateMaxStars` в контроле `StarRatingControl` проверяет, чтобы максимальное количество звезд рейтинга не было отрицательным или равным нулю.

### 4. Для чего и как используют делегат CoerceValueCallback?

**В WPF:**
CoerceValueCallback (колбэк принуждения/коррекции) используется для корректировки значения свойства на основе других свойств или внутреннего состояния объекта, если новое значение выходит за логические рамки. Исключения при этом не выбрасываются — значение просто "сглаживается". Вызывается после ValidateValueCallback.

**В Avalonia UI:**
Передается как параметр `coerce` при регистрации `AvaloniaProperty`. В проекте этот подход ярко продемонстрирован в `RangeSlider`: метод `CoerceLowerValue` гарантирует, что нижний ползунок никогда не перейдет за верхний ползунок, корректируя значение "на лету" прямо в момент перетаскивания.

### 5. Какие типы маршрутизируемых событий есть в WPF (поясните каждый)?

**В WPF:**
Существует три стратегии маршрутизации (Routing Strategies):
1. **Bubbling (Поднимающиеся/Пузырьковые):** Событие возникает на элементе-источнике и "всплывает" вверх по визуальному дереву к корневому элементу (Window). Это самый частый тип (например, `Click`).
2. **Tunneling (Туннельные):** Начинаются от корневого элемента (Window) и спускаются вниз по визуальному дереву к элементу-источнику. Обычно имеют префикс "Preview" (например, `PreviewMouseDown`). Позволяют родительским элементам перехватить и отменить событие до того, как оно достигнет цели.
3. **Direct (Прямые):** Подобны обычным событиям .NET. Срабатывают только на том элементе, где возникли, и никуда не маршрутизируются (например, `MouseEnter`).

**В Avalonia UI:**
Архитектура событий полностью совпадает с WPF. В фреймворке реализованы те же три стратегии маршрутизации: `Bubble`, `Tunnel` и `Direct`.

### 6. Как создать RoutedEvent?

**В WPF:**
1. Регистрируется статическое поле через метод `EventManager.RegisterRoutedEvent`.
2. Указывается имя события, стратегия маршрутизации, тип делегата обработчика и тип владельца.
3. Создается обычная CLR-обертка `event` с блоками `add` и `remove`, которые вызывают внутренние методы `AddHandler` и `RemoveHandler`.

**В Avalonia UI:**
Вместо класса `EventManager` используется вызов `RoutedEvent.Register<TOwner, TEventArgs>`. В нашем кастомном элементе `AnimatedCourseCard` (файл `AnimatedCourseCard.axaml.cs`) созданы все три вида событий: `CardHoveredEvent` (Direct), `CardPreviewClickedEvent` (Tunnel) и `CardClickedEvent` (Bubble).

### 7. Поясните концепцию Command в WPF? В чем ее преимущества?

**В WPF:**
Команды — это реализация паттерна Command (основанная на интерфейсе `ICommand`), которая позволяет отделить логику действия от интерфейса (от кнопки или пункта меню). 
**Преимущества:**
- **Разделение логики и UI:** Поддержка архитектуры MVVM. 
- **Повторное использование:** Одно и то же действие можно вызвать откуда угодно (из контекстного меню, главной панели, через горячие клавиши).
- **Управление состоянием:** Если метод интерфейса `CanExecute` возвращает `false`, все элементы управления, привязанные к этой команде, автоматически становятся неактивными (серого цвета).

**В Avalonia UI:**
Интерфейс `ICommand` и его смысл остаются неизменными. Команды — основа MVVM-архитектуры Avalonia.

### 8. Как используются команды?

**В WPF:**
1. В классе ViewModel создается свойство типа `ICommand` (на практике часто используют сторонние реализации, например, `RelayCommand`).
2. В XAML-разметке это свойство привязывается к атрибуту `Command` элемента управления: `<Button Command="{Binding SaveCommand}" />`.
3. Опционально передается аргумент через свойство `CommandParameter="{Binding SomeData}"`.

**В Avalonia UI:**
Подход абсолютно аналогичен. Вместо самописных `RelayCommand` в нашем проекте используются реактивные команды `ReactiveCommand` из библиотеки ReactiveUI (встроена в Avalonia), которые биндятся к кнопкам в XAML точно так же: `Command="{Binding AddCourseCommand}"`.

### 9. Как создать RoutedUICommand?

**В WPF:**
`RoutedUICommand` — это класс, встроенный в WPF. Он представляет собой команду, которая маршрутизируется по визуальному дереву в поисках обработчика (`CommandBinding`). Главная особенность: он имеет свойство `Text`, позволяющее инкапсулировать название команды для UI.
Создается он как статическое поле:
```csharp
public static readonly RoutedUICommand MyCommand = new RoutedUICommand(
    "Текст команды",    // Text
    "MyCommand",        // Name
    typeof(MyWindow),   // Тип владельца
    new InputGestureCollection() { new KeyGesture(Key.S, ModifierKeys.Control) } // Сочетания клавиш
);
```

**В Avalonia UI:**
Avalonia UI идеологически отказалась от концепции *маршрутизируемых* команд (`RoutedUICommand`), так как они нарушают строгую чистоту MVVM, смешивая логику визуального дерева и бизнес-логику.
Однако, чтобы продемонстрировать понимание концепции "команды, имеющей имя и текст", в нашем проекте был создан кастомный класс `CustomCommand` (в файле `Utils/AppCommands.cs`). Он реализует интерфейс `ICommand`, содержит в себе свойства `Name` и `Text`, а также логику выполнения. Эта команда привязана к кнопке "Справка" (Help) в главном меню приложения.
